## Why

The current dashboard editor (`/dashboard/campaigns/[id]/edit`, from `add-campaign-page-builder`) works, but two gaps limit it: every edit writes straight to the live `pageConfig` the public page reads, so owners can't safely experiment without immediately affecting real visitors, and the layout (all section forms shown inline at once, a plain type-picker dropdown to add sections) doesn't scale well as a page-building experience. This change restructures the editor around the interaction patterns of Perspective (app.perspective.co) — a focused three-zone layout, a categorized block library, canvas-level section selection — and, more importantly, introduces a real draft/publish separation so edits are staged before they go live.

## What Changes

- **Editor layout restructure** into three zones: a top bar (campaign name, link back to the dashboard, desktop/mobile preview toggle, unpublished-changes indicator, primary Publish button), a left sidebar (ordered section list; selecting a section reveals its edit form; add/delete/reorder controls), and a centre canvas (the existing non-interactive `PageRenderer` preview, presented prominently on a neutral background). Snowball's own visual identity is kept — only the interaction pattern (zones, selection model, block library) follows Perspective, not its visual styling.
- **Bidirectional selection**: selecting a section in the sidebar highlights it on the canvas, and selecting it on the canvas highlights the matching sidebar entry.
- **Block library**: the current add-section dropdown is replaced with a categorized panel of visual tiles (icon + label), one per section type, grouped as "Content" (Hero) and "Referral mechanics" (Leaderboard, Reward tiers, Countdown). No new section types are introduced in this change.
- **Canvas hover controls**: hovering or selecting a rendered section on the canvas shows a small floating control strip with move-up, move-down, and delete (no duplicate — duplicating a Leaderboard or Countdown section isn't meaningful).
- **Device preview toggle**: switches the canvas between desktop width and a ~390px mobile width. This only constrains the preview container; it never changes what's saved.
- **Draft vs. published state** (the core of this change): a new nullable `Campaign.pageConfigDraft` JSON column, added via a Prisma migration. All editor edits — section content, order, presence, and the page-level Hero headline/subtext and Countdown end date — autosave into `pageConfigDraft` (debounced, one shared timer across fields, never a request per keystroke), never directly into the published fields. The public `/c/[slug]` page continues to read only the published `Campaign.headline` / `description` / `endsAt` / `pageConfig` columns and never touches `pageConfigDraft`; this is a structural guarantee (the public code path has no reference to the draft column at all), not a runtime check that could be bypassed. Pressing **Publish** copies the draft into the published fields and clears the draft. **Discard** clears the draft without touching the published fields, reverting the editor to what's currently live. If no draft exists, the editor initializes from the published state. A top-bar indicator shows save progress (saving / unpublished changes / failed to save); a failed autosave never discards the owner's edits — they remain editable locally and are retried on the next edit or an explicit Retry.
- `Campaign.status` (`DRAFT`/`ACTIVE`, governing whether the campaign is running at all) is completely unrelated to this new draft/publish concept and is not touched by this change — the distinction is documented explicitly in design.md to prevent the two from being conflated later.
- **Production rollout requires baselining first.** This project has never used Prisma's migration workflow — schema changes to date all used `prisma db push`, so neither `snowball-dev` nor production has any migration history. Before this change's own migration is created, both databases are baselined via `prisma migrate resolve --applied 0_init` (generated with `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`), a one-time manual step. Skipping this would risk `prisma migrate dev` treating the live, un-baselined database as drifted and offering to reset it (destroying data), and would make a naive `prisma migrate deploy` in production a silent no-op that never creates the column. Once baselined, a new `vercel-build` script (`prisma migrate deploy && next build`) applies pending migrations automatically at each Vercel deploy; a dedicated task then confirms the column actually exists in production by direct query, rather than assuming a green build means it worked.

**Assumptions recorded here for review** (implementation details the request didn't spell out; correct any of these via `/opsx:update` before implementation starts):
- **Autosave (confirmed)**: only Publish and Discard are explicit button presses; everything else autosaves via one shared debounce timer. See design.md's Decisions for the save-state indicator and failure-handling details.
- **Discard placement**: a secondary "Discard draft" control next to the Publish button in the top bar, visible only when a draft exists. The request asks for "a way to discard the draft" without specifying where.
- **Add-block panel presentation**: an inline expandable panel triggered by an "Add block" affordance in the sidebar (not a modal) — keeps the interaction lightweight and consistent with the sidebar-driven editing model.
- **`pageConfigDraft`'s actual shape bundles more than section layout**: it stores `{ headline, description, endsAt, pageConfig: { sections } }` — the full set of page-editable content — not just the section list. This is necessary so that editing Hero's headline or the countdown's end date is also properly staged as a draft (both currently live on `Campaign.headline`/`description`/`endsAt`, outside `pageConfig`); otherwise those edits would leak to the public page immediately, contradicting the required "editing a section and saving does NOT change the public page until Publish is pressed" behavior. The column name stays `pageConfigDraft` as requested even though its contents are broader than `pageConfig` alone.
- **Publish with no draft returns an error** (400 "No draft to publish") rather than silently succeeding as a no-op, to avoid masking a client-side bug where the Publish button was enabled with nothing to publish. **Discard with no draft succeeds as a no-op** (200), since a defensively-clicked discard shouldn't be an error.

## Capabilities

### Modified Capabilities
- `campaign-page-builder`: the editor's interaction model is restructured (three-zone layout, block library, canvas selection/hover controls, device toggle) and gains the draft/publish lifecycle (save-to-draft, publish, discard, unpublished-changes indicator).
- `public-campaign-rendering`: gains an explicit guarantee that the public page never renders unpublished draft edits — it reads only the published `pageConfig` (and now also only the published `headline`/`description`/`endsAt`), regardless of what draft state exists.

### New Capabilities
- None.

## Impact

- **Code**: `PageBuilderEditor.tsx` is substantially rewritten into the new three-zone layout with new sub-components (top bar, sidebar with accordion + block library, canvas with selection/hover chrome, device-width container); `PageRenderer.tsx` gains an opt-in `editable` mode used only by the canvas (adds per-section selection/hover chrome; the public rendering path and existing preview-only usage are unaffected when the prop is omitted); `src/lib/pageConfig.ts` gains a `PageDraftEnvelopeSchema` and a `parseDraftEnvelope` normalizer; `PATCH /api/campaigns/:id` accepts an optional `pageConfigDraft`; two new routes, `POST /api/campaigns/:id/publish` and `POST /api/campaigns/:id/discard-draft`; `prisma/schema.prisma` gains `pageConfigDraft Json?` on `Campaign` via a new migration; `package.json` gains a `vercel-build` script.
- **Data**: a one-time baseline migration (`0_init`, describing the schema as it already exists, applied via `prisma migrate resolve --applied` rather than run) against both `snowball-dev` and production — required because neither database has any migration history today — followed by one additive, nullable-column Prisma migration (`pageConfigDraft`). No backfill needed — existing campaigns simply have no draft until first edited. The new migration is applied to `snowball-dev` locally via `prisma migrate dev`; applied to production automatically at deploy time via `prisma migrate deploy` in the new `vercel-build` script, with its presence confirmed afterward by direct query.
- **Compatibility**: the existing 12 Playwright E2E flows must keep passing unmodified. Four new flows are added: editing-and-autosaving does not change the public page until Publish; Publish then does change it; Discard restores the published state; the device toggle changes preview width without altering saved data.
- **Verification**: `npm run typecheck`, `npm run build`, and the full E2E suite (existing + new) must pass; the migration must be applied to `snowball-dev` only during development; after pushing, the Vercel deployment must succeed (running the new migration against production automatically) and `https://snowball-blue.vercel.app/c/launch-giveaway` must be manually confirmed rendering correctly in production.
- **Phasing**: this is large enough to warrant explicit phases — see design.md's Migration Plan. Each phase ends with the full current E2E suite passing before the next phase begins.
